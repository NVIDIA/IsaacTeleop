# Docs — agent notes

## Ecosystem partner cards are data, not markup

Cards on `overview/ecosystem.rst` are generated by the `partner-grid` directive
(`source/_ext/partner_grid.py`) from `source/_data/partners.yaml`. Add or change a
partner by editing that YAML and dropping a logo in `source/_static/partner-logos/` —
never by hand-writing card markup or a hard-coded count into the `.rst`. Controlled
field values and the required schema are documented at the top of the YAML file.

Cards are grouped by `section`, and the page renders one grid per section in the order
`partner_grid.SECTIONS` declares. Adding a section therefore touches the extension and
the page, not just the data. Reserve `platform` for NVIDIA's own stacks and teams —
everything third-party belongs in `active` or `upcoming`.

Within a section, only the `platform` band is hand-ordered through `order`; partner
sections sort alphabetically by `organization`, and the build rejects an `order` on those
records rather than let a dead field imply a ranking. Keep the YAML records in the order
they render.

## The platform band shows a handle, not a logo

Cards in `section: platform` render no logo panel and no status pill: four NVIDIA
eye-marks and four "Active" pills only repeated the section heading. They carry a
`handle` instead — the role that stack plays, in two or three words, as a chip — and the
build rejects `logo`, `new_until`, or any lifecycle but `maintained` on them rather than
accept a field that renders nowhere. Release numbers go in a quoted `version`, which
renders as a suffix after the title, not in the description.

## Each band has a fixed card shape, and the build enforces it

The three bands are deliberately different, so a field that one band renders is rejected
in another instead of being quietly ignored: `platform` takes a `handle` and no `logo`,
`upcoming` takes no `description` and may carry no `links` at all, and only `active` uses
the full shape. Unknown keys fail too, so a note cannot be smuggled in as a new field —
extend the schema in `partner_grid.py` and document it in the YAML header instead.

## The partner-card preview carries a copy of the card, and has to be kept in step

`source/_static/tools/partner-card-preview.html` is a standalone page partners open to check
their own logo and copy before they send it. It has to work as one offline file, so it
carries its own copy of the card markup, the card CSS, and the theme's `--pst-*` values.
A change to the card in `ecosystem.css` or `partner_grid.py` therefore has to be mirrored
there — a preview that no longer predicts the page is worse than none. Its width switcher
uses widths measured off a real build (380px desktop, 318px once the right-hand TOC
appears, 343px phone); measure again rather than guess if the layout moves.

The "Become a Partner" steps on `overview/ecosystem.rst` link it as a plain relative path
into `_static`, which is why it stays in the same tab and shows no external marker: it is
a page on this site, not somewhere else.

It hardcodes the partner submission form URL, and keeps an "or email it to us" fallback
next to it because `forms.gle` is unreachable from mainland China, where a good share of
these partners sit. Keep the fallback if you touch that copy.

## Supported devices are a table, and not the same thing as a partner card

`overview/ecosystem.rst` ends with a device table generated by `device-matrix` from
`source/_data/devices.yaml`. Devices are looked up rather than browsed, so the break from
the card grids above is deliberate: keep it a table.

A row and a card answer different questions, so neither file derives from the other and a
company may appear in both. The row's device name *is* the manufacturer link, which is
why no row carries a separate "Overview" link. Rows render in file order within their
group, so there is no `order` field to keep in sync.

Each row's third column is a Details disclosure, and its panel holds exactly three
columns — set up, requirements, acquire — in that order for every device. That panel is
where setup links, the prerequisites the table itself has no room for, and manufacturer
contacts live; entries are noun phrases, not sentences, and the build rejects a trailing
period. Anything longer than a phrase belongs on the device's own page under
`source/device/`, linked from the panel.

## The external marker follows the target, not the record

The docs site and the IsaacTeleop repository are both this project, so a link into either
renders with no arrow and no screen-reader "(external)" — tracking links included. Only
third-party domains get the marker, and other GitHub organizations (`isaac-sim`) count as
third-party. `partner_grid.PROJECT_REPO` is the one place that boundary is written down.

## Ecosystem section headings need an explicit target

The count pill is part of the heading text, so the auto-generated slug carries the number:
`#partners` becomes `#partners-15` and changes whenever a card is added or removed. Every
section on that page therefore gets a `.. _label:` target, which is what inbound links
and `#supported-input-devices` rely on. Add one with any new section.

## Never wrap styled layout in `.. container::`

Docutils renders `container` as `class="docutils container"`, and Bootstrap claims the
same class name, so the theme ships
`.docutils.container {padding-left: unset; padding-right: unset}`. That outranks a
plain class selector and silently flattens horizontal padding — panels end up with
text flush against their border. Use the `eco-block` directive (or the `eco_block`
node from Python) for any element the CSS pads.

## Ecosystem interactivity is HTML and CSS, never JavaScript

The docs ship no `html_js_files`. Interactive affordances use platform features instead:
the cards' contact panel is a native `[popover]` with a `popovertarget` button, which
gives light dismiss, Esc, focus return, and top-layer rendering for free, and the device
table's Details rows are a `<details>` per row sharing one `name`, which is what closes
the open panel when the reader opens another.

Two rules keep that disclosure working. The panel is a *sibling* grid item, revealed by
`.device-action:has(details[open]) + .device-panel`, so it can span all three columns and
so the device name stays a plain link — a link inside a `<summary>` both navigates and
toggles. And the reveal lives in `@supports selector(:has(*))`, so a browser without it
renders every panel open rather than hiding the content; reuse that pattern instead of
reaching for a script.

When docutils has no node for the element you need, give `eco_block` an `html_tag` and
`html_attributes` rather than emitting a `nodes.raw` blob, so the contents stay real
nodes for non-HTML builders.

## Build with warnings as errors

`make current-docs` runs `sphinx-build -W --keep-going`, which is what CI runs. A new
warning fails the build, so check a docs change with that command rather than a bare
`sphinx-build`.
